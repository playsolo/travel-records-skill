# Travel Records 真实 Gmail 验收流程

在 Codex 里连接自己的 Gmail，选一段已知行程，验证 Travel Records 能从真实邮件和附件产出可核对的住宿与消费记录。全程在 Codex 和本地核对报告里完成，无需 FotoNest。

## 1. 连接 Gmail 并安装 Skill

在 ChatGPT 桌面版的 **Plugins** 里启用 Gmail 插件并连接要测试的 Google 账号。已有连接可以直接使用，多个账号时指定一个。在准备使用的项目目录安装 Skill 和 Python 依赖，再打开一个新的 Codex 对话。

[OpenAI 插件连接说明](https://learn.chatgpt.com/docs/plugins) · [Travel Records 中文安装说明](https://github.com/playsolo/travel-records-skill/blob/main/README_ZH.md)

以下命令适用于 macOS/Linux。需要 Node.js 和 Python 3.9 或更新版本。

```bash
npx skills add playsolo/travel-records-skill --skill travel-records --agent codex
python3 -m venv .venv
.venv/bin/python -m pip install jsonschema
```

## 2. 选一段真实行程，先记下你知道的答案

开始提取前，按[加载与交付检查](../references/execution-and-delivery.md)确认实际读到技能和必要引用文件、输出目录可写，并说明附件发布是否可用。读取失败不能算技能已加载；只能回贴内容时，不能称为已提供下载附件。

选一次自己记得的旅行，或先指定一两家酒店和大致时间。最好能在 Gmail 找到预订确认和最终账单，方便对照。用 Gmail 核对至少一笔已知的入住、退房、币种、总额和订单状态。账单邮件可能晚于入住几个月，指定搜索时要区分**住宿日期**和**邮件发送日期**。如果已知哪封邮件是转发或取消，也记下它供验收。

## 3. 用 Gmail 做首次读取

在 Codex 的对话里选择 **@Gmail**，替换下面的括号内容后发送：

> 用 @Gmail 和 travel-records，针对我指定的 Gmail 账号整理［酒店或行程范围］。已知住宿日期是［日期范围］。只在这个行程范围内找预订确认、取消、酒店水单和发票。先从［酒店名称、邮件日期范围或我指定的 Gmail 搜索条件］查起。读取匹配邮件的正文及相关附件，读不到的列为待复核。按同一订单合并转发、账单和发票，独立订单保留。住宿晚数按日期去重，金额以账单为准，无反证时可用预订报价并注明依据。用 `.venv/bin/python` 在本地运行核对，将会话、旅行 CSV 和核对 JSON 保存到 `travel-review-private/`。CSV 包含入住退房日期、晚数、状态、金额、币种、金额依据和来源。验证两个文件可以打开，再提供文件链接，并简述搜索范围、实际读取数量及待复核项。这个测试只读取邮箱，所有核对结果留在本地。

如果希望验证后续补入账单的效果，可以在首轮仅指定预订确认的查询，下一轮再给出相应账单的搜索条件。记录首轮的报告路径。若 Gmail 连接不可用或授权账号选错，先解决连接问题，再开始验收。

## 4. 补充证据并重跑

1. 有后续账单、取消或修改邮件时，在同一个对话里让 Agent 用原订单线索继续通过 Gmail 查找，沿用同一份会话，说明哪些字段更新了。
2. 在同一个对话让 Agent 用相同查询、同一份会话再跑一次。比较最后两次报告的订单身份、状态、日期、晚数和金额。

## 5. 判定结果

打开 `travel-review-private/` 下 Agent 给出的 `latest.json`，用其中的 `review_file` 找到核对报告。对照 `records`、`acceptance.nights`、`spending` 和 `coverage`，以及 Gmail 原文。

| 测试项 | 通过标准 |
| --- | --- |
| 技能加载 | 实际读取完整入口及本次所需引用，使用已有脚本和正式 schema。 |
| 文件交付 | CSV 和核对 JSON 已保存并回读。支持文件发布时，能从回复链接打开同一轮结果；发布受限时，明确记录限制，小批结果可完整回贴文件内容，但不算下载附件验收通过。聊天表格用于浏览摘要。 |
| 连接和读取 | 找到至少一笔已知的真实住宿，实际读到正文。相关附件能读取时已核对，无法读取时有明确原因及待复核项。 |
| 住宿和费用 | 入住、退房、状态和币种与已知原件一致。同一订单的水单、发票和转发件只计一次。两间房有独立费用时可相加，同一晚只计一次。 |
| 补充证据 | 有最终账单的订单采用账单金额。有取消证据的订单在历史里显示为取消，其未发生的住宿不计晚数。若没有对应真实资料，标记该场景为未覆盖。 |
| 重跑 | 使用同样的查询和会话，再次运行的订单 ID、日期、状态、晚数和金额一致。 |
| 完成判定 | 运行 `run_session.py assert-complete`。有未读、已读未提取、未翻页、未检索账号或未解决复核项时不能通过；manifest 的 `state=ready` 与 `processing.status` 分别反映文件可用和处理状态。 |
| 年度范围 | `scope.email_years` 仅含用户指定邮件年份，每次搜索和补查均带同样边界；不因入住发生在该年就自动搜其他年邮件。用户扩展年份后重新出现待检索年份，追加证据仍沿用原记录 ID。 |
| 连续执行 | 有已配置且实际可用的同步 host adapter 时，验证 worker 每次返回后控制器仍能继续下一批；“done”文本不清空队列。连续无进展应为 stalled，不能伪称完成。未接入 adapter 时标记该能力未验收。 |
| 中断恢复 | 用真实失败记录或合成断连验证 `failure` 的幂等记录和有界重试。失败项不应阻塞其他候选；重试耗尽后保留阻碍，恢复后仍沿用原 session 和记录身份。没有发生该场景时标为未覆盖。 |
| 来源和覆盖 | 每条采信结果能回到相应邮件或附件。从发现清单生成覆盖审计，运行 `audit_coverage.py`，分别报告发现数、读取数、各处置数量及导出条数。若达到读取上限或还有下一页，保留进度并标明尚未检查的范围；校验通过但有 `needs_review` 不能称为已全部解析。 |

**验收记录**　记下从安装到首份报告的耗时、搜索范围、命中及实际读取数量、抽查订单数、通过项、未覆盖项和需要手动修正的字段。反馈时使用脱敏摘要。合成邮件只作为可选的离线回归样例。

## 6. 单独检查自主发现能力

已知酒店、日期和消息 ID 的专项修正，只能验证指定材料的读取、归并与导出。要检查防遗漏效果，先由验收人独立保存小范围内的答案，再在新的提取会话中只提供授权邮箱、宽于目标入住的邮件时间窗口和记录类别，不提示目标酒店、确切入住日期或消息 ID。包含同一邮件串的多次入住、跨月住宿及事后账单；答案不交给提取方。使用独立私有会话保存产物，验证后再决定是否接续原档案，避免重复导入。

对照独立答案检查目标住宿是否自主发现、不同入住是否分开、房数与日期并集晚数是否正确，并检查每个候选的最终去向。分别记录检索未命中、已命中未读取、读取失败、已读取未提取和已提取未导出的情况；无历史记录的环节标为无法判定。不要用 schema 或覆盖审计通过替代召回率与字段正确性核查，也不要把提示过答案的同一会话重跑称为盲测。
